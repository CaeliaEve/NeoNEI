## 目标与边界

修复历史浏览失效；消除未预热页面阻塞翻页；显著缩短首次打开配方的等待；使默认浏览顺序对应目标游戏环境实际使用的 NEI 顺序。

保留 optimize 风格的紧凑布局、原生像素、完整配方目录、候选项及在线/离线能力。复用已验收 Catalog，不重新执行数小时的配方或纹理导出。历史报告及现有工作区改动不覆盖。

| 问题 | 代码/数据事实 | 影响 |

## 方案比较与推荐

1. **只修接线与等待、扩大缓存**：投入较小，能修历史和卡住问题；首次配方依然需要临时关联数据，优化上限有限。
2. **推荐：生成轻量交互数据，配合可取消的优先调度和共享原生图集**：把确定性整理工作提前完成；点击只定位目录、读取当前内容与绘制。需要调整数据访问与渲染接口，但无需修改已验收 Catalog。
3. **全部解码常驻内存**：最有利于热访问，但浏览图集解码本身约 1.29 GiB，另有配方、索引与 GPU 开销，启动与资源压力很大，不采用。

推荐方案先修可独立交付的历史/翻页问题，再替换配方关键路径。持久化压缩文件与有界解码缓存分开管理，不用无限预热换取性能。

## 一、历史浏览修复

- 建立共享的 `Catalog ID + item ID -> 浏览实体 + 原生帧` 查询，主浏览区、历史区与配方静态物品图标共用身份和纹理信息。
- 历史区把实际条目传入有效的 Catalog 渲染分支，恢复左键查产出、右键查用途、提示、去重和最近浏览优先。
- 持久化 item ID 等稳定身份，不持久化易变的图集位置。重载后从当前包解析 sprite。
- 历史按 Catalog 隔离；旧 `viewHistory` 只迁移当前 Catalog 能确认存在的身份，保留旧存储供恢复。缺失身份不误映射到其他物品。
- 维持两行和最多 400 条的现有习惯。历史区可见项参与当前可见内容的优先加载。

## 二、翻页与原生图标绘制

### 交互与图片解耦

- `residentPage()` 只返回目标行与总数，图片就绪不作为返回条件。
- 每个交互请求带代次；只有最新代次能更新页面、命中区域与图片。收到旧结果直接丢弃。
- 滚轮事件累计目标页，按动画帧合并渲染；跳过用户快速滚过的中间页。立即更新目标页，不逐页排队等待。
- 目标条目的名称、身份和点击行为不依赖预热。图片未到时只显示该目标条目的待加载状态，不用旧图冒充新页。
- 加载失败必须结束 pending 并显示可识别的重试状态，不能无限停留在预热中。

### 图集级调度

- 优先级：当前配方/当前浏览页/可见历史 > 下一次明确交互 > 相邻页 > 后台压缩文件缓存。
- 当前页按图集合并请求与绘制，采用 `drawImage(atlas, sourceRect, targetRect)`；避免每个图标等待独立 `createImageBitmap` 裁剪。
- 初始保留现有按钮与提示命中语义，使用可复用 Canvas。先消除串行图片工作，不引入不必要的 GPU 框架重写。
- 原生帧维持 16/32/64 尺寸；Canvas 禁用平滑，CSS 使用像素化显示，避免低分辨率中间层。
- 排队任务可真正移除；共有下载保留消费者引用，仅当没有消费者时取消。不能因旧页取消而中止新页也需要的同一图集。
- 当前页请求可提升已排队任务的优先级。解码无法中途停止时允许完成，但不得绘制过期页面。
- 低优先级缓存全部约 50.4 MiB 的压缩浏览图片到本地存储；只解码当前工作集。缓存未准备完也允许浏览。
- 搜索与模组过滤复用同一顺序索引；大跨度跳页与反向滚动同样遵守最新目标优先。

### 排序与图集布局联动

确认 NEI 顺序后按新浏览邻接关系重新打包原生帧，避免只调整行顺序导致一页命中大量分散图集。帧内容保持无损；记录每个可见页所需图集数和实际解码量。搜索造成的分散请求仍由优先队列处理。

## 三、配方加载关键路径

### 从既有 Catalog 生成独立的交互包

交互包使用独立目录和版本，绑定 Catalog ID、生成器版本与文件哈希。其用途是提前整理数据，不重新解释游戏规则。

- **导航目录**：item/fluid -> 产出/用途 -> 分类、准确数量、完整有序 recipe IDs；使用紧凑整数引用，避免大量重复长 ID。
- **配方分块**：包含当前配方的槽位、候选引用、数量、概率、必要条件、布局及首帧引用。按合理字节上限分块，避免每条配方一个请求，也避免每次读取整类大数据。
- **共享资源表**：分类、机器、物品、流体、文本、视图和纹理描述统一引用，不把全部机器列表与大段 related 复制到每条配方。
- **扩展资源**：完整动画轨迹、未展开的候选图片、机器详情等独立按需加载。必要配方语义不能因延迟加载而丢失。
- 生成过程核对所有目录、方向、分类数量、recipe IDs 与原 Catalog；保持超过 100 条等大分类完整可达。输出大小、生成耗时和峰值资源实测记录。

### 点击时只做当前需要的工作

1. 点击传入明确方向；只将该方向当前配方列为首屏依赖。
2. 从常驻目录定位分类与配方，读取一个相关分块，复用共享记录。
3. 首屏静态物品帧优先复用浏览图集。用完整帧引用匹配，不用物品名或近似图替代；未覆盖的资源读取原 Catalog。
4. 数量、概率、候选数与当前配方必要条件同时到位后，记为原生首屏可用。动画可随后启动并独立记录时间。
5. 当前分类相邻配方、当前页明确悬停项、最近历史低优先预取；不枚举所有物品的双向配方。

相同配方的在途读取去重。按 Catalog、方向、分类及配方身份缓存，所有取消与切换遵守代次。重构激活的 Catalog 路径，移除它对旧 dist-data/runtime/image API 的探测依赖。

### 内存、持久化与离线

- 共享原生图集池统一记账；建议初始解码纹理预算 192 MiB，测量后仅在确有必要时调整。不是将浏览与配方两个上限简单相加。
- 配方数据热缓存建议上限 64 MiB；常驻导航索引另行统计与设限。超过预算优先降低预取量，不降采样图标。
- Cache Storage/IndexedDB 保存压缩文件，读取、哈希校验、解码与主线程提交分开计时；同一内容避免在相邻层重复校验。
- 在线与离线使用同一交互包读取协议。`/offline` 同时记录必需交互资源的完整性与 ready 状态；不能把仅有浏览缓存误报为完整离线可用。
- 包不存在时走显式的现有数据路径并报告该状态，不能静默显示“极速就绪”。损坏或版本不匹配的包拒绝使用。

## 四、NEI 默认排序

目前无法从缺失的 order 字段还原游戏精确顺序。按中文名称、模组名或数字 ID 猜测不能称为 NEI 默认排序。

1. 优先检查已有、可验证且匹配环境的 NEI 顺序证据。本轮按文件名搜索归档尚未找到明确可用的排序快照，这不证明所有归档都不存在该数据。
2. 如无证据，仅轻量采集目标 NEI 在默认排序配置下实际显示的有序物品列表及分组配置；需要确认目标 NEI 的排序实现，不能直接假定 `ItemList.items` 即最终显示顺序。
3. 用 registry、meta、规范化 NBT 等完整身份映射当前 Catalog item ID，记录映射成功、原生列表未包含、歧义等数量；无法确认的身份不猜配。
4. 派生独立 order map，绑定游戏环境与 Catalog。折叠组以首个可见成员的原生位置为基准，组内候选也遵守原生顺序；搜索保留相对顺序。
5. NEI 原生列表没有的网页流体/派生条目保留访问能力并稳定追加，不插入原生序列中；明确标记该扩展规则。
6. 对匹配的原生子序列做完整顺序比对；抽查组内 meta/NBT 差异和过滤结果。拿到证据前，将精确排序保持为待完成项。

## 性能验收口径与目标

下面是本机环境的工程目标，尚非实测承诺。固定浏览器、缩放、页面大小、样本、排序、数据版本和缓存状态做改前/改后比较。

| 场景 | 目标与完成定义 |
| --- | --- |
| 任意翻页操作响应 | 目标页码/身份在 1–2 帧内响应（60 Hz 环境目标 P95 <= 33 ms） |
| 已解码页完整原生图片 | P95 <= 100 ms |
| 压缩文件已缓存、尚未解码的页 | 完整原生图片 P95 <= 200 ms |
| 已准备配方 | 必需语义与可见原生首帧 P95 <= 100 ms |
| 交互包已就绪、未预热的配方 | 同一首屏定义，P95 <= 500 ms；重点消除当前数秒等待 |
| 全空缓存首次访问 | 单独记录下载、目录准备、图集读取与解码；不混入热访问指标，不承诺任意网络下零等待 |

每个场景记录样本数、P50/P95/max、错误数、请求/解码量；尾延迟超目标必须解释。图片完成按实际可见槽位绘制和像素核验判断，不只检测 DOM 或弹窗出现。

## 轻量验证

实现前先为这次缺陷补少量行为测试，不建立庞大回归框架：

- 历史记录恢复、左右键方向、去重、刷新和 Catalog 隔离。
- 人为延迟图集读取时分页仍返回；100 次快速滚轮、反向和远跳只提交最终目标，旧页队列能退出；失败后可继续导航。
- 单方向打开不等待另一方向；同 ID 共享读取；分类/配方完整目录与现有结果一致，验证大于 100 条分类的尾页。
- 原生帧无缩放、图集边界与关键可见像素；重打包时利用既有逐帧审计检查所有源帧。
- 排序完整子序列和代表性分组对照；离线保存后停服、断网并重开验证历史、配方和浏览。
- 连续浏览期间记录缓存字节、活跃/排队任务，确认有上限且离开页面释放引用。

运行产品必要的 typecheck、受影响测试和 build；浏览器验收使用一套小型场景脚本与固定样本，复用既有验收数据。不重复全量游戏导出。

## 实施顺序与交付

1. **先恢复基本交互**：历史接线与 ID 解析；分页返回解除图片等待；最新目标代次与可取消优先队列；同条件基线和定向验证。
2. **完成速度重构**：派生交互目录/配方块；单方向首屏；图集级绘制和浏览/配方共用原生帧；持久化与离线读取一致。
3. **完成游戏排序与整体验收**：顺序采集/映射、新顺序原生图集打包、轻量像素/语义/连续交互验收，实测达到目标后更新本地入口。

排序采集可与前两步独立推进，但必须在最终图集布局和排序验收前完成。每步输出实际变更、同条件数据及未达项目；不因某个预热样本很快而宣称所有冷页无感。

交付包含实现文件、版本化派生包、顺序映射与像素核验、轻量性能报告及本地可运行入口。历史证据和原 Catalog 保持可追溯；无需用户再手动转交整轮配方导出任务。
